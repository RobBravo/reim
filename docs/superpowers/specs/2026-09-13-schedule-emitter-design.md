# Emitting installable schedules — design

`reim pipeline list` has printed a suggested cron expression per source since the
MVP, and nothing has ever consumed it. An operator wanting per-frequency
scheduling has to read a 23-row table and hand-write the crontab. This increment
closes that gap: `reim pipeline schedule` emits a crontab fragment ready to
install, covering ingestion and the alert check.

This is v0.5.0's third increment. Everything measured below was checked against
the repository on 2026-09-13.

## 1. What exists, and what this adds

Measured, not assumed:

| Piece | State |
|---|---|
| `DEFAULT_CRON_BY_FREQUENCY` (`reim/domain/pipelines/scheduling.py`) | A cron expression per `Frequency`, UTC, offered "as a starting point for operators wiring REIM into cron". Consumed by exactly one caller |
| `reim pipeline list` (`reim/cli/main.py:172`) | That one caller — prints a `SUGGESTED CRON` column in a human-readable table. Nothing turns it into an installable schedule |
| `PipelineRunner.run_all` (`reim/ingestion/runner.py:86`) | Already accepts `keys: list[str] \| None`, and runs them **sequentially**, each in its own transaction |
| `ConnectorRegistry.keys` (`reim/ingestion/registry.py:85`) | `enabled_only` filter; no frequency filter anywhere |
| `reim pipeline run-all` (`…/main.py:224`) | Runs every enabled pipeline. No way to run a subset by cadence |
| `PipelineScheduler` (`…/scheduling.py:29`) | A `Protocol` with **no implementation**, and none is added here — see §5 |
| README "Scheduling" | Documents one cron line running `run-all` monthly, and states REIM has "no built-in scheduler by design" |
| `reim alert check` | Shipped last increment; needs its own cron line, which nothing emits |

The addition is **one CLI command, one CLI option, one pure module** and its
tests. No new dependency, no model, no migration.

### 1.1 The gap this closes, stated precisely

Today's documented deployment is a single line:

```text
0 13 5 * * cd /opt/reim && .venv/bin/python -m reim.cli pipeline run-all
```

That runs all 23 enabled pipelines once a month. The two daily exchange-rate
sources therefore update monthly, and the eight annual sources are fetched
twelve times a year for data that changes once. The catalog already records
every source's real cadence and `DEFAULT_CRON_BY_FREQUENCY` already maps cadence
to a cron expression — the only missing piece is something that puts the two
together into text an operator can install.

### 1.2 Four frequencies, not seven

`Frequency` defines seven values. The enabled catalog uses **four**:

| Frequency | Enabled pipelines | Default expression |
|---|---|---|
| `monthly` | 11 | `0 13 5 * *` |
| `annual` | 8 | `0 13 15 4 *` |
| `daily` | 2 | `0 13 * * *` |
| `quarterly` | 2 | `0 13 10 1,4,7,10 *` |

The emitter iterates the frequencies **actually present among enabled sources**,
not the enum. A crontab carrying three lines for cadences no source uses is
noise an operator has to reason about and then delete (D3).

## 2. The command

`reim pipeline schedule` writes a crontab fragment to stdout. Nothing is
installed, nothing is written to a file, and no privileged path is touched: the
operator reviews the text and pipes it where they want it. That is deliberate —
a tool that edits a live crontab is a tool that can silently delete one (D6).

```text
reim pipeline schedule [--working-dir PATH]
```

Output shape — one commented block per frequency, then the alert line. The
real output of `reim pipeline schedule --working-dir /opt/reim`, verbatim (no
block elided — none is long enough to need it):

```text
# REIM — generated by `reim pipeline schedule`. Review before installing.
# Times follow the cron daemon's timezone; the defaults were written as UTC.

# daily — 2 pipeline(s): banguat_exchange_rate, bcn_exchange_rate
0 13 * * * cd /opt/reim && .venv/bin/python -m reim.cli pipeline run-all --frequency daily

# monthly — 11 pipeline(s): cepalstat_cpi_monthly, cepalstat_exchange_rate_monthly, cepalstat_monetary_monthly, cepalstat_rates_monthly, imf_imts_costa_rica, imf_imts_el_salvador, imf_imts_guatemala, imf_imts_honduras, imf_imts_nicaragua, imf_imts_panama, inide_cpi_monthly
15 13 5 * * cd /opt/reim && .venv/bin/python -m reim.cli pipeline run-all --frequency monthly

# quarterly — 2 pipeline(s): cepalstat_bop_quarterly, sieca_services_trade
25 13 10 1,4,7,10 * cd /opt/reim && .venv/bin/python -m reim.cli pipeline run-all --frequency quarterly

# annual — 8 pipeline(s): cepalstat_debt_annual, cepalstat_gdp_annual, worldbank_ni_cpi_inflation, worldbank_ni_exchange_rate, worldbank_ni_exports, worldbank_ni_imports, worldbank_ni_remittances, worldbank_ni_reserves
45 13 15 4 * cd /opt/reim && .venv/bin/python -m reim.cli pipeline run-all --frequency annual

# Alerting — after the ingestion window, since staleness is only meaningful once the day's ingestion has finished.
0 15 * * * cd /opt/reim && .venv/bin/python -m reim.cli alert check
```

The header says "Review before installing" rather than claiming a timezone the
tool cannot enforce: cron runs in the host's timezone, `DEFAULT_CRON_BY_FREQUENCY`
was only *written* against UTC, and §8 already commits to leaving that
reconciliation to the operator. Restating "Times are UTC" in the header would
contradict that.

The comment naming each block's pipelines is the part that makes the output
reviewable. An operator reading `--frequency monthly` cannot otherwise tell what
it will run, and the whole point of this command is to be read before it is
installed.

## 3. Staggering, because the defaults collide

Every expression in `DEFAULT_CRON_BY_FREQUENCY` fires at minute 0 of hour 13,
and `daily` fires *every* day. So with the defaults installed verbatim, daily
and monthly both start at 13:00 on the 5th; daily and quarterly both start at
13:00 on 10 January; daily and annual both start at 13:00 on 15 April.

`run_all` is sequential, so this is two REIM processes each working through its
own list rather than a thundering herd — but it is still two sweeps contending
for the same database and, where a source serves several pipelines, the same
host. There is no reason to accept that when the fix is free.

**The emitter gives each frequency its own minute, and changes nothing else
about the expression.** `DEFAULT_CRON_BY_FREQUENCY` remains the sole authority
on *which days* a cadence runs; the emitter rewrites only the minute field, and
every offset stays inside the hour so the day fields cannot be perturbed:

```text
daily 0 · weekly 5 · monthly 15 · quarterly 25
semiannual 35 · annual 45 · irregular 55
```

Ordered by how often the cadence runs, so `daily` keeps `:00` — it fires most
often and is the one that should never move. Seven distinct minutes are needed
even though four are used today, because the mapping is over the enum and a new
source may introduce a cadence at any time.

This is policy the catalog does not state, and it is the emitter inventing it
(D4). It is recorded here rather than buried because an operator who wants a
different window will look for exactly this paragraph.

## 4. The one supporting change

`run-all` gains `--frequency`, taking a `Frequency` value and restricting the
run to enabled pipelines of that cadence.

This needs **no change to `PipelineRunner`**: `run_all` already accepts
`keys: list[str] | None` (`runner.py:87`), so the CLI filters the catalog and
passes the keys. The filter belongs in the CLI because the catalog is what knows
a source's cadence, and `ConnectorRegistry.keys` has no reason to grow a
frequency parameter for one caller (D5).

`--frequency` is independently useful: it is how an operator re-runs just the
daily sources after fixing a network problem, without a 23-pipeline sweep.

## 5. What is deliberately not built

**`PipelineScheduler` stays unimplemented.** The README states REIM has "no
built-in scheduler by design", and that remains true: the operator's cron is the
scheduler, and this command only writes down what to give it. Implementing the
Protocol with an in-process APScheduler would mean a new dependency, a
long-lived process to supervise and restart, and a contradiction of a design
statement the project has published since the MVP (D1).

The Protocol keeps its value as documentation of the seam. Nothing in this
increment forecloses implementing it later, because nothing here depends on how
the schedule is executed.

**No systemd renderer.** Cron is universally available and the README already
documents it; a systemd timer needs a `.service` and a `.timer` per job, which
is eight files for four cadences and an awkward thing for a command to print. A
cron line translates to a timer trivially, and the reverse does not hold (D2).
The internal `ScheduleEntry` list is nevertheless the seam a renderer would
consume, because that shape is what makes the emitter testable — not because a
second format is planned.

## 6. Shape and testing

One pure module, `reim/domain/pipelines/schedule.py`:

```text
ScheduleEntry(comment: str, expression: str, command: str)
build_schedule(catalog, *, working_dir, python) -> list[ScheduleEntry]
render_crontab(entries) -> str
```

Pure: a catalog and some strings in, text out. No session, no clock, no
settings, no filesystem — so every rule below is unit-tested directly, and the
CLI command is a thin wrapper that resolves `--working-dir` and prints.

What the tests pin:

* Only frequencies present among enabled sources produce a block — constructing
  a catalog whose sources are all monthly must yield exactly one ingestion
  block, not seven.
* Each block's minute is offset per §3, and **the day fields are untouched** —
  compare the emitted expression's day/month/weekday fields against
  `DEFAULT_CRON_BY_FREQUENCY`'s, so a future edit that rewrites more than the
  minute fails.
* Two blocks never share a minute.
* The comment names the pipelines the block will run, and that list matches what
  `--frequency` would select. A comment that drifts from the command it
  describes is worse than no comment.
* Disabled sources are absent entirely rather than commented out, and no
  parameter exists to include them — a catalog of nothing but disabled sources
  yields no ingestion blocks at all.
* The alert line is emitted last and after the ingestion window.
* The emitted text is a valid crontab shape: five whitespace-separated schedule
  fields then a command.

This list originally promised a test for "no line exceeding what cron
accepts"; it is dropped rather than added, because there is no single number
to assert against. Cron implementations disagree on a line-length limit — some
historical `cron`s cap a line at 1024 bytes, `cronie` reads lines dynamically
with no practical cap — and the field this module actually controls, the
schedule-plus-command line, does not grow with the catalog: only the
human-readable comment above it lists pipeline names, and that comment is not
what any cron parses into a job. Asserting a length against an unspecified
limit would encode a number nothing else in this spec justifies.

The catalog-derived cases use a constructed `SourceCatalog`, not the real one —
the real catalog's frequency mix is data that will change, and a test asserting
"four blocks" would fail the day someone adds a weekly source. One test does
read the real catalog, to assert every frequency it contains has an entry in
`DEFAULT_CRON_BY_FREQUENCY`; that is the invariant worth pinning against real
data.

## 7. Decisions

| | Decision | Rationale |
|---|---|---|
| **D1** | Emit schedules; do not implement `PipelineScheduler` | The README has stated "no built-in scheduler by design" since the MVP. An in-process scheduler means a dependency and a daemon to supervise (§5) |
| **D2** | crontab only, no systemd renderer | Cron is universal and already documented; a timer is two files per job, eight for four cadences. A cron line translates to a timer trivially; the reverse does not (§5) |
| **D3** | Iterate frequencies present among enabled sources, not the `Frequency` enum | Three blocks for cadences no source uses is noise the operator must read and delete (§1.2) |
| **D4** | The emitter offsets each cadence's minute, and only the minute | All four defaults fire at 13:00 and `daily` fires every day, so they collide by construction. `DEFAULT_CRON_BY_FREQUENCY` stays the authority on which days (§3) |
| **D5** | `--frequency` filters in the CLI, not in `ConnectorRegistry` | `run_all` already takes `keys`; the catalog is what knows a cadence, and the registry does not need a parameter for one caller (§4) |
| **D6** | Print to stdout; never install, never write a file | A tool that edits a live crontab can silently delete one. The operator reviews and pipes (§2) |
| **D7** | Each block names the pipelines it will run | `--frequency monthly` is otherwise opaque, and this output exists to be read before it is installed (§2) |
| **D8** | Disabled sources are never scheduled, and there is no flag to include them | The catalog records why a source is off, and `disabled_reason` may be a licence that forbids redistribution. A commented cron line invites uncommenting without reading that; a flag that emits one is worse, because a crontab runs unattended. An operator wanting to see what is disabled has `reim pipeline list` (§6) |

## 8. Out of scope

* **Installing or editing crontabs.** D6.
* **systemd, launchd, Kubernetes CronJob, CI schedules.** D2. The `ScheduleEntry`
  list is the seam if one of them is ever wanted.
* **Per-pipeline schedule overrides in the catalog.** Cadence comes from
  `frequency`; a source needing its own window is a case nobody has yet.
* **Timezone handling.** Cron runs in the host's timezone and
  `DEFAULT_CRON_BY_FREQUENCY` documents itself as UTC; the emitted header says
  so, and reconciling the two is the operator's call.
* **Verifying the schedule is installed.** REIM cannot see the operator's
  crontab, and `reim pipeline status` already answers "did it actually run".
